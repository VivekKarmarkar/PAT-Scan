❯ ok now here's the real question for you... how exactly do you interact with   
  PDF documents?                                                                

● Great question — and it's exactly the right question to ask before designing
  the skills roadmap, because the answer shapes everything.

  There are two fundamentally different paths I can take with a PDF, and they
  have very different strengths:

  Path 1 — The Read tool (multimodal, native)

  I can pass a .pdf file directly to my Read tool. When I do that:

  - The PDF is rendered and fed to me as visual input — I literally see the
  pages, figures, equations, tables, and layout the way a human reader would.
  - I can also read the embedded text stream on the same pass, so I get text and
   image simultaneously.
  - Hard limit: max 20 pages per request. For any PDF longer than 10 pages, I'm
  required to specify a pages parameter (e.g., pages: "1-20", then "21-40",
  etc.).
  - No external library, no parsing step — the content lands in my context
  directly.

  Strength: I can answer questions about figures, handwritten marginalia,
  equation typesetting, layout, color-coded diagrams — anything visual.
  Weakness: paginated access only, and large papers eat context fast.

  Path 2 — The pdf skill (programmatic)

  There's a plugin skill called pdf designed for transformations and bulk
  extraction. It uses Python libraries (likely pypdf, pdfplumber, pdf2image,
  etc.) to:

  - Extract text and tables into plain strings/CSV
  - Split, merge, rotate, watermark
  - Render pages to PNGs for archival
  - Create new PDFs from scratch

  Strength: scales to 200-page documents without blowing my context, and
  produces artifacts (text files, images) that other skills can consume.
  Weakness: text extraction loses layout fidelity, and figure extraction via
  libraries is famously messy — equations become gibberish, two-column layouts
  interleave, etc.

  The architectural implication for your roadmap

  Look at your 18 skills through this lens:

  ┌─────────────────────────────┬────────────────────────────────────────────┐
  │            Skill            │                 Best path                  │
  ├─────────────────────────────┼────────────────────────────────────────────┤
  │ /ask-questions-about-paper  │ Path 1 — I need to see the figures to      │
  │                             │ answer                                     │
  ├─────────────────────────────┼────────────────────────────────────────────┤
  │ /find-evidence-in-paper     │ Hybrid — Path 2 to locate text, Path 1 to  │
  │                             │ verify in visual context                   │
  ├─────────────────────────────┼────────────────────────────────────────────┤
  │ /extract-text-from-paper    │ Path 2 — produces a reusable artifact      │
  ├─────────────────────────────┼────────────────────────────────────────────┤
  │ /extract-figures-from-paper │ Path 2 — render pages to PNG, then Path 1  │
  │                             │ to identify which are figures              │
  ├─────────────────────────────┼────────────────────────────────────────────┤
  │ /paper-to-website           │ Path 2 — needs durable assets (text +      │
  │                             │ image files)                               │
  └─────────────────────────────┴────────────────────────────────────────────┘

  ★ Insight ─────────────────────────────────────
  - The 20-page limit is why /unix-philosophy-decompose (item 4 in your list) is
   load-bearing, not cosmetic. A 60-page paper literally cannot be understood in
   one Read call — it must be chunked, each chunk summarized into a durable
  artifact, then the artifacts composed. Your roadmap author (past you) already
  intuited this.
  - There's a subtle third path worth knowing about: I can see images. So if the
   pdf skill renders pages 1-80 as PNGs to disk, I can then Read individual PNG
  files one at a time without the 20-page-per-call ceiling — effectively
  bypassing the limit by materializing pages as image files first. This is how
  /extract-figures-from-paper likely has to work.
  - Chen-tactile tomography-1.pdf in your folder is 26 MB — almost certainly >20
   pages and visually dense. It will be the stress test for whichever approach
  you pick. Start the skills design with that paper in mind and the others will
  be easy.
  ─────────────────────────────────────────────────

  So: which path do you want to lean on? Or do you want to deliberately build
  the infrastructure around both, with a clean contract between them?
